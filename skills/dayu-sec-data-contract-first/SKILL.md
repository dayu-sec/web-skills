# Data Contract First

## 概述

本 Skill 约束“按数据契约写代码”的场景。只要用户、接口文档、生成代码、类型声明、接口注释或项目内已验证实现已经给出明确结构，就以该结构作为解析、映射、校验、展示和错误处理的依据。

默认原则：契约优先于猜测，单一真源优先于多路径兜底。不要用防御式代码掩盖契约不一致。

## 引用入口

- [使用 Zod 进行运行时校验](references/runtime-validation-with-zod.md)：处理外部 JSON、运行时配置、持久化数据、事件载荷或其他不可信边界时读取。

## 契约来源

可作为数据契约的来源包括：

1. 用户在当前任务中明确给出的 JSON、字段结构、示例响应或错误结构。
2. OpenAPI、Swagger、接口文档或官方服务文档中的声明。
3. 生成代码中的接口注释、请求/响应声明和 SDK 类型。
4. 项目内类型定义、字段定义、事件载荷声明和表单模型声明。
5. 项目内已经验证且有明确来源说明的 payload、response、error 结构。

优先级从高到低：

1. 用户当前明确说明。
2. 官方接口文档、OpenAPI 或 Swagger。
3. 生成代码、SDK 声明、类型定义和接口注释。
4. 项目内已验证实现。
5. 未验证的运行时观察、常见字段名、命名习惯和经验猜测不得作为契约。

## 工作流

任务涉及 `zod`、运行时 Schema 或不可信输入校验时，先读取 [使用 Zod 进行运行时校验](references/runtime-validation-with-zod.md)。

在实现或评审数据处理逻辑前，先写出：

- 契约来源：例如“用户提供的响应示例”“OpenAPI 响应声明”“生成类型 `DetailResponse`”“现有已验证历史接口”。
- 本次消费的字段路径：例如 `attachments`、`record.extra_info.name`、`error.details[].description`。
- 字段必需性：必需、契约声明可选、契约声明条件存在。
- 是否存在多结构兼容：若存在，说明每个分支的来源和适用条件。

随后只按列出的字段路径实现解析、映射、表单回填、事件载荷读取或校验逻辑。若契约不明确，先查文档、生成代码、类型声明或现有调用；不要用猜测式 fallback 替代确认。

## 解析与映射规则

- 只读取契约声明的字段路径，不顺手追加同义字段、复数变体、历史猜测或常见命名。
- 契约声明为必需字段时，不要用长可选链吞掉契约问题；让不一致暴露出来，或按项目通用异常路径处理。
- 契约声明字段可选时，可以按该可选性处理空态，但要说明可选性来自契约。
- 空态、缺省展示和用户体验文案可以存在，但不得伪装成契约字段存在，也不得掩盖服务端或调用方违背契约。
- 当用户明确要求“不要防御式编程”“按契约收敛”或类似要求时，主动删除无来源 fallback、猜字段和过度兼容分支。

## 兼容分支

只有以下情况允许多结构兼容：

- 用户明确说明存在多个结构。
- 文档、OpenAPI、Swagger 或生成类型声明了联合结构、灰度结构或版本差异。
- 项目内已有经验证的历史接口兼容需求，并能指出来源。
- 第三方接口文档明确存在返回差异。

每个兼容分支必须说明：

- 来源：历史接口、灰度阶段、第三方差异、文档声明或用户说明。
- 适用条件：何时进入该分支。
- 消费字段路径：该分支读取哪些字段。
- 保留原因：为什么现在还需要兼容。
- 退出条件：如果已知，说明何时可以删除。

没有来源的兼容分支不保留。不要为了“稳妥”兼容文档和用户都没有提到的结构。

测试以当前生效的对外或运行时契约为目标；保留兼容逻辑不等于要按历史字段增删、命名或版本演进逐一编写用例。除非当前契约明确承诺持续支持某种旧结构，否则不要把历史变更过程固化为常规回归测试。

## 服务异常

局部业务错误提示只解析已约定的业务错误结构。

例如约定结构为 `error.details[].description` 时，只从该路径提取业务文案。不要再拼接 `error.message`、框架默认错误、传输层错误或任意猜测字段作为业务提示。

非约定错误包括：

- 网络、超时、取消、传输层异常。
- 框架或请求库默认错误对象。
- 未知错误结构。
- 格式异常、服务端非约定响应或契约不一致。

这些错误应进入项目通用失败路径。可以按项目约定记录日志、抛出异常或展示通用失败文案，但不得伪装成具体业务错误。

## 反模式

不要写无来源 fallback：

```ts
row.name || row.title || row.label
```

如果契约只声明 `row.name`，就只消费 `row.name`。`title` 和 `label` 需要明确来源才可保留。

不要把框架错误当业务错误：

```ts
error?.response?.data?.error?.details || error?.message || '失败'
```

如果业务错误契约是 `error.details[].description`，就只解析该路径；其它错误走通用失败处理。

不要猜详情附件结构：

```ts
detail.attachments || detail.files || detail.list || detail.object_id
```

如果契约声明 `attachments` 数组，就只消费 `attachments`。其它字段必须有文档、用户说明或历史兼容来源。

不要用可选链吞掉必需结构：

```ts
record?.extra_info?.name ?? ''
```

如果契约声明 `record.extra_info.name` 为必需字段，按该路径处理；若当前代码可能拿不到，先暴露契约不一致并确认原因。

## 正确示例

- 已知详情结构包含 `attachments` 数组时，只读取 `attachments`，不猜 `files`、`list`、`object_id`。
- 已知回填字段为 `record.extra_info.name` 时，按该路径回填；不确定时先查类型或接口文档。
- 已知错误结构为 `error.details[].description` 时，只用该路径生成局部业务提示；未知错误继续走通用失败。
- 已知生成类型只声明 `displayName` 时，只消费 `displayName`，不添加 `name`、`title`、`label` 候选。
- 已知请求 payload 中 `status` 是契约声明的枚举字段时，只提交声明枚举值；不要猜额外状态。
- 已知接口注释声明 `profile.nickname` 可为 `null` 时，按该 nullable 契约处理空态；不要顺手读取 `profile.name`。
- 已知灰度阶段同时存在 `items` 和 `records` 时，分别标注灰度来源、适用版本或服务端条件，再实现兼容。

## 输出要求

说明实现或评审结论时，先给出：

```text
契约来源：...
消费字段路径：...
兼容分支：无 / 有，来源为...
错误处理：业务错误路径为...；其它错误走通用失败
```

如果故意不做兼容，明确说明这是按当前契约收敛实现。若发现代码与契约不一致，指出不一致位置并要求确认，不用新 fallback 静默掩盖。

## 评审检查

评审数据处理代码时重点检查：

- 是否出现没有来源的 `a || b || c` 字段候选。
- 是否用可选链吞掉契约声明的必需结构。
- 是否把 `error.message`、请求库默认错误或未知对象拼成业务文案。
- 是否存在没有来源、条件和保留原因的兼容分支。
- 是否把真实接口地址、真实业务 payload、客户或人员信息写进长期 Skill 内容。

## 修改边界

本 Skill 不改变项目架构、应用装配、路由、菜单、版本或制品。实际实现数据解析、表单回填、事件载荷处理和服务异常逻辑时，应留在当前任务所属的应用和模块内。

任务涉及微前端宿主、子应用、生命周期或跨应用契约时，同时使用 `$dayu-sec-web-micro-frontend`；本 Skill 只约束数据契约的消费方式。

不要把项目特定 payload、真实接口、内网地址、账号、Token、客户信息、人员信息、本地代理或正在变化的项目状态写进 Skill。
