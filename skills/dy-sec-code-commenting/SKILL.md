本 Skill 约束 AI Agent 在写代码时同步生成和维护注释。目标不是增加注释数量，而是让后续维护人员能快速理解代码的功能、意图、使用方法、边界和维护风险。

核心原则：注释解释代码无法稳定表达的背景和约束。不要把清晰代码逐行翻译成自然语言，也不要用过时注释制造误导。

## Code Commenting

- 输出或修改源码时，必须随代码写注释。
- 类、函数、方法、组件、Hook、Props、公共接口和公共类型等“重”契约，使用块级注释或文档注释，并紧邻声明。
- 变量、关键语句和局部逻辑等“轻”实现，使用行注释，并紧邻代码。
- 禁止在源码末尾集中补注释或追加总结式注释。

## 注释原则

- 优先说明“为什么这样做”“适用于什么边界”“调用方如何使用”“修改时不能破坏什么约束”。
- 按项目既有风格和语言原生形式写注释，例如文档注释、docstring、块级注释或行注释；不要为了统一而破坏本仓库习惯。
- 中文团队或中文项目中，代码注释默认使用中文；必要的专有名词、API、包名、协议名和代码标识保留英文，避免为了翻译损失准确性。
- 不把未确认假设写成事实。兼容、兜底、临时绕过和历史约束要写清来源、适用条件和可删除条件。
- 不在注释中写入内网地址、真实域名、账号、Token、客户信息、人员信息或本地临时环境状态。

## 函数与模块注释

公共函数、复杂私有函数和模块入口优先使用块级或文档注释，至少覆盖：

- 职责：这段代码负责什么，不负责什么。
- 使用方式：调用方应在什么场景使用，传入什么形态的数据。
- 边界：输入约束、输出语义、空态、异常、幂等性、权限或环境前提。
- 副作用：网络请求、持久化、全局状态、缓存、事件、计时器、订阅或资源释放。

不要机械列出每个参数。参数含义已经由名称和类型表达清楚时可省略；存在枚举含义、单位、格式、生命周期、调用顺序或来源限制时必须说明。

## 内部注释

函数内部只在维护成本高的位置写行注释：

- 多步数据转换：按阶段说明“当前阶段要收敛什么结构”。
- 多分支规则：说明进入分支的业务原因，而不是复述条件表达式。
- 顺序敏感逻辑：说明为什么必须先做 A 再做 B。
- 异常和兜底：说明错误归属、是否可恢复、为什么不继续向下执行。
- 性能或资源取舍：说明缓存、批量处理、懒加载、节流、防抖或清理策略的理由。

行注释应解释决策，不解释表面赋值。

## UI 与组件代码

组件、页面、控制器或视图层代码只在职责边界和交互流程不明显时补注释：

- 顶层组件或页面入口：说明承载的用户流程、数据来源和职责边界。
- 公开 props、slots、events、callbacks 或 render hooks：说明业务语义、默认行为、调用时机和兼容约束。
- 复杂模板、条件区域、批量操作工具栏、权限门禁、加载失败和空态组合：用简短注释说明结构块意图。
- 纯展示布局、简单样式和直观控件组合不强制注释。

## 反模式

不要写无信息量注释：

```ts
// 给 name 赋值
const name = user.name;
```

应改为解释约束，或直接不写：

```ts
// 展示名来自账号主档案，不能回退到昵称，避免审计记录前后不一致。
const displayName = user.profile.displayName;
```

不要让注释和实现分叉：

```ts
// 最多重试 3 次
const maxRetries = 5;
```

不要把猜测写成事实：

```ts
// 旧系统一定返回 legacyId
```

如果只能确认是兼容分支，写清条件：

```ts
// 兼容迁移期旧载荷；当上游全部切到 id 后删除 legacyId 分支。
const id = payload.id ?? payload.legacyId;
```
