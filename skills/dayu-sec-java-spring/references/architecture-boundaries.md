# 架构与边界

## 先识别现有架构

- 从包结构、依赖方向、构建模块、应用入口和测试确认仓库采用简单分层、DDD、六边形或其它模式。
- 保持目标仓库既有命名；不要为了套模板批量移动包或重命名所有类。
- 对非简单业务优先围绕业务能力组织包，再在能力内部区分层次，避免所有 Controller、Service 和 Repository 堆在全局技术目录。
- 只有当前变更确实需要时才引入新抽象；一个实现、无替换需求且边界稳定的代码不必机械增加接口。

## DDD/分层职责

| 层 | 负责 | 不负责 |
| --- | --- | --- |
| facade/adapter-in | HTTP、消息入口、请求绑定、身份上下文、响应映射 | 业务规则、持久化细节 |
| application | 用例编排、事务边界、权限用例、端口调用、结果协调 | 框架传输细节、核心不变量 |
| domain | 实体、值对象、聚合、不变量、领域服务、仓储端口 | Spring MVC、JPA、外部 DTO |
| infrastructure/adapter-out | 仓储实现、数据库映射、外部客户端、消息、技术配置 | 决定业务规则 |

允许依赖方向：入口适配层和基础设施依赖应用/领域；应用依赖领域；领域不依赖外层。

## 对象边界

- 请求 DTO 只包含调用方可提交的字段，并承载格式、必填、长度和范围等传输校验。
- 响应 DTO 只包含公开契约字段，不直接返回领域实体、JPA Entity/PO 或外部服务响应。
- 领域实体维护身份、生命周期和不变量；值对象优先不可变并在创建时验证自身约束。
- PO/JPA Entity 只表达持久化映射；外键、懒加载和审计字段不泄漏到 API。
- 外部 DTO 按上游契约单独建模，防止上游字段变化污染本服务领域模型。
- 转换器放在拥有适配责任的边界；显式映射语义不同的字段，MapStruct 等工具只消除机械复制。

## 应用服务与领域规则

- 一个应用方法对应一个清晰用例：加载状态、授权、调用领域行为、保存并发布结果。
- 把跨字段、状态机、资格判断、金额/评分计算等业务不变量放入领域实体、值对象或领域服务。
- Controller 不直接组合多个 Repository；Repository 实现不反向调用应用服务。
- 领域事件表达已发生的事实，命名使用过去式；命令表达意图，不把事件当同步 RPC。
- 应用异常可以携带用例失败语义，但领域层使用领域错误或结果类型，不依赖 application 异常和 HTTP 状态。

## 仓储端口

- 在领域或应用边界定义面向用例的仓储接口，返回领域对象、值对象或只读投影。
- 基础设施实现封装 `JpaRepository`、MyBatis Mapper、SQL、分页对象和数据库异常。
- 查询方法命名表达业务意图；复杂动态查询使用 Specification、QueryDSL、MyBatis 动态 SQL 或明确查询对象，避免通用 `Map<String, Object>`。
- 批量读写明确顺序、去重、失败语义和内存上限。

## 依赖和配置

- 使用构造器注入和 `final` 依赖，避免 `@Autowired` 字段注入。
- 配置类只装配技术组件，不承载业务流程。
- 避免循环依赖；出现循环时重新检查职责和事件边界，不启用延迟注入掩盖问题。
- 引入新依赖前确认仓库是否已有等价能力、许可证、维护状态、依赖树和运行时体积。

## 架构验证

- 使用编译依赖、包扫描或 ArchUnit 等仓库已有方式验证依赖方向。
- 搜索 domain 对 Spring MVC、JPA、facade、application DTO 和 infrastructure 包的导入。
- 搜索 Controller 对 Repository、PO/JPA Entity 和外部 Client 的直接依赖。
- 搜索公开 API 直接返回持久化对象或外部 DTO 的位置。
