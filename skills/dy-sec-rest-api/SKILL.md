# REST API

## 工作顺序

1. 先读取目标仓库的 `AGENTS.md`、接口规范、OpenAPI、生成类型、已有端点和调用方，确认当前契约及兼容边界。
2. 把需求改写为资源、资源关系、状态变化和操作语义；不要先从控制器方法名或页面按钮反推 URL。
3. 确定 URI、HTTP 方法、成功状态码、幂等性、请求参数、请求体、响应体和错误映射。
4. 先更新或生成 OpenAPI 契约，再实现服务端与客户端；代码优先仓库则同步更新注解并导出契约，始终只保留一个可验证的真源。
5. 实现输入校验、权限检查、业务规则和异常转换，保持传输层、应用层和领域层职责分离。
6. 验证正常、空集合、非法参数、未认证、无权限、资源不存在、冲突、限流和内部错误等路径。
7. 运行仓库已有的 OpenAPI lint、契约测试、构建和测试命令，报告实际证据。

## 契约优先级

按以下顺序确定当前任务的契约：

1. 用户在当前任务中的明确要求。
2. 目标仓库的 `AGENTS.md`、已发布规范和经确认的 OpenAPI。
3. 生成代码、SDK、接口测试和已发布客户端契约。
4. 目标仓库中已经验证的实现。
5. 本 Skill 的通用规则。

发现冲突时明确列出冲突位置、现有调用方影响和迁移方案。不要用额外包装层、别名字段或多路径解析静默掩盖冲突。新接口默认按本 Skill 收敛；已发布接口先保护兼容性，再通过版本化或弃用流程迁移。

## 资料路由

- 设计资源、路径、HTTP 方法、状态码、自定义动作或幂等性时，读取 [resource-http-semantics.md](references/resource-http-semantics.md)。
- 设计字段命名、过滤、排序、分页、时间或语言参数时，读取 [naming-query-pagination.md](references/naming-query-pagination.md)。
- 设计请求体、成功响应、错误体或校验错误时，读取 [request-response-errors.md](references/request-response-errors.md)。
- 编写 OpenAPI、处理认证授权、安全、版本化或兼容演进时，读取 [openapi-security-evolution.md](references/openapi-security-evolution.md)。

只读取当前任务直接需要的 reference。涉及现有明确契约的数据解析和映射时，同时使用 `$dy-sec-data-contract-first`；涉及 Java/Spring 服务端实现时，同时使用 `$dy-sec-java-spring`。

## 不可破坏的约束

- 静态资源路径使用小写复数名词和 `kebab-case`；路径变量、Query 参数和 JSON 字段使用 `snake_case`。
- 成功响应直接返回资源或规定的集合结构，不增加 `code`、`message`、`data` 等通用成功包装层。
- 失败响应使用标准 HTTP 错误码，并返回包含 `error.status` 与 `error.details[]` 的错误对象。
- 方法语义、状态码和幂等性保持一致；异步受理使用 `202 Accepted`，并提供可查询的任务或操作资源。
- 列表接口只选择一种分页模型，稳定排序并限制最大页大小；空集合返回空数组，不返回 `null`。
- 时间点使用 ISO 8601/RFC 3339 表达，优先 UTC；绝对时间不得用无时区语义的字符串冒充。
- OpenAPI 描述真实运行时行为；不要让注解、YAML、控制器和客户端生成类型长期分叉。
- 不在示例、错误体、日志或文档中暴露账号、Token、内部地址、堆栈、SQL、客户或人员信息。

## 评审检查

- 检查 URL 是否表达资源而非控制器动作，嵌套是否确有从属关系。
- 检查 `GET` 是否安全、`PUT` 和 `DELETE` 是否幂等、`POST` 重试是否有去重策略。
- 检查 `201`、`202`、`204`、`400`、`401`、`403`、`404`、`409`、`429` 和 `5xx` 是否按真实结果使用。
- 检查 JSON 命名、分页信封、错误状态枚举和日期格式是否与契约一致。
- 检查校验、认证、授权、资源归属和并发冲突是否覆盖，不把所有失败都映射为 `200` 或 `500`。
- 检查 OpenAPI 是否声明参数位置、必需性、格式、枚举、响应状态、错误模型和安全要求。
- 检查兼容分支是否有来源、适用版本和退出条件。

## 输出要求

设计或实现接口时，至少说明：

```text
资源与操作：...
契约真源：...
方法与路径：...
成功响应：HTTP ...，响应结构为...
失败响应：HTTP ... -> error.status ...
幂等与并发：...
兼容性：无 / 有，迁移方式为...
验证：...
```

评审时按严重度报告问题，给出具体端点、契约字段或代码位置，并区分规范违规、兼容性风险和可选改进。
