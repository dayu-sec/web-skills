# 无效测试形态

这里的形态都能跑通、都是绿的、都会被计入用例数量，但它们不执行被测逻辑，因此既拦不住缺陷，又在正常重构时制造红灯。识别它们比多写几条用例更重要。

## 形态一：源码文本断言

把源文件当字符串读进来，用正则匹配其中的片段：样式属性、JSX 属性、`import` 语句、函数签名、接口路径字面量、某段实现文本。

**为什么诱人。** 它不需要渲染环境、不需要造输入、不需要理解被测逻辑，一条断言就能"覆盖"任意文件，而且几乎总能一次写绿。在缺少可执行入口、或者急于给一次改动补上用例时，这是阻力最小的路径，AI 协作下尤其容易成批产出——模型能读到源码文本，却不一定能运行它。

**失败形态。**

- **零拦截。** 不调用任何被测逻辑，业务缺陷一条都发现不了，却在报告里占据覆盖面。
- **等价重构即红。** 抽函数、换等价写法、改类名、挪文件都会让它失败，于是团队养成"改测试让它绿"的习惯，测试从此不再是判据。
- **可能从诞生起就不成立。** 这类断言常与实现同一次提交写入，却从未匹配过实现文本。因为没人把它当行为看，红灯被长期当作待修项挂着。
- **互相矛盾而不被发现。** 一处断言要求某段文本出现、另一处要求同样的文本不出现，两者都能通过编译与运行，只有同时跑测试才会撞上。断言的是文本而非行为，冲突没有任何其它机制能暴露。
- **把一次实现固化成规范。** 它锁住的是"源码长什么样"，直接与重构对立。

**识别信号。** 断言的入参来自读文件的结果；正则里出现样式属性、JSX 属性、`import`、函数签名或目录名；用例名在描述页面结构与布局；用"不得出现某段文本"来表达架构约束；一个用例里连续十几条针对同一文件的正则。

## 形态二：变更探测器

断言一个常量等于它自己的字面量拷贝，或断言配置对象与用例里抄写的副本一致。改一次要改两处，永远不会发现缺陷，只会增加改动成本。区别在于：断言**转换结果**有价值，断言**声明本身**没有。

**最常见的载体是声明式清单**：菜单与导航配置、路由表、枚举与字典、字段与列清单、权限码表。它们的共同点是"内容会随产品常规演进而变，但读取它们的逻辑不变"。

**为什么诱人。** 这类清单是用户可见的，断言它看起来就像在断言用户看到的东西，因此不容易被识别成无效形态——这是它比形态一更难自查的原因。但用户看到的是"导航能把我带到正确的页面"，不是"第二项叫什么、排第几"。前者是读取逻辑的输出，后者是清单自己。

**失败形态。**

- **常规演进即红。** 调顺序、改名、加一项都会让它失败，而这些恰恰是这类清单最频繁的变更。
- **红灯长期挂着。** 破坏它的提交通常与它无关（一次纯粹的重排、改名），提交者不认为自己动了被测逻辑，红灯于是被留在原地；后来者看到常红的用例，学到的是"红是正常的"。
- **把编辑成本转嫁给无关改动。** 改一次清单要同时改用例，长此以往人们倾向于不改清单。

**识别信号。** 用例读取真实的配置文件或常量表，再把其中一部分抄成期望值；断言里出现 `deepEqual(list.map(...), [...])` 且数组内容就是清单自己；断言某项的标题、顺序、下级数量或是否存在；用例名在描述"清单里有什么"而不是"读取它之后会发生什么"。

**怎么改写。** 问一句：**这条断言在检查声明长什么样，还是在检查读取它的逻辑算出了什么？** 前者删掉；后者保留，但把输入换成用例自己构造的清单，而不是仓库里那份真实配置——这样逻辑仍被覆盖，真实清单怎么变都不影响它。

## 形态三：结构存在性用例

断言某些文件存在、某些旧路径不存在、目录按某种方式组织。目录调整是常规演进，这类用例把它变成一次测试维护；而真正的风险（引用断裂）由类型检查与构建更早暴露。

## 形态四：接线断言

断言组件调用了国际化函数、注册了某个 Hook、引入了某个 Provider。它证明的是代码写了这一行，不是功能可用——文案缺键、命名空间写错、Provider 顺序不对时它照样是绿的。

读取多语言 JSON 文件并断言键集对齐、插值变量一致或字符集合规，同属此类。这些是 i18n 工作过程中的文件维护事项，由 `dayu-sec-web-i18n` Skill 在开发时指导同步，不通过自动化测试守护。

## 形态五：过宽快照

把整棵渲染树或整个响应对象存成快照。任何无关变动都会让它失败，久而久之快照被无条件更新，等于没有断言。快照只用于小范围、语义明确、人工可读的输出。

## 形态六：组件渲染与交互断言

把组件渲染成 DOM 或字符串，断言其中的结构、`aria-label`、`title`、类名、样式规则，或者模拟点击、键盘、滚动再断言结果。

**为什么诱人。** 它看起来最接近"用户真正看到的东西"，因此比前几种更理直气壮；渲染一次能断言很多条，覆盖率涨得快。在重业务应用里，这份直觉是错的：用户看到的正确性由组件库、浏览器和真实运行验证共同保证，业务仓库重复一遍并不增加保障。

**失败形态。**

- **拦不住业务缺陷。** 它执行的是组件库的渲染逻辑，不是本仓库的业务规则。字段算错、权限判错、状态流转错时，它照样渲染得出来、照样绿。
- **换组件库或升版本即集体变红。** 断言的是渲染出的结构与属性，而那是上游的实现细节；一次小版本升级就能让一批用例同时失败，而产品行为并没有变。
- **把样式决策焊死。** 断言 `box-sizing`、`min-width`、固定行高、溢出裁剪这类规则，等于规定实现只能这么写，后续任何视觉调整都要先改用例。
- **伪装成源码文本断言。** 没有渲染环境时，同样的意图会退化成读源文件正则匹配 `className`、`onClick`、图标名、JSX 片段——形态一与本形态实为同一件事的两种写法，都应清退。

**识别信号。** 引入 `react-dom/server`、测试用 DOM 库或自建 `document`；断言 `aria-label`、`title`、`className`、CSS 属性；用例名在描述"渲染出什么""点了之后怎样""布局如何收缩"；断言源码里有没有某个图标名、某个 JSX 属性、某段 `onClick`。

**怎么处理。** 直接删。如果它想守的是一条业务规则（例如"无权限时不出现该入口"），把规则从组件里提取成可调用的判定函数，用输入输出重写；视觉与交互本身交给真实运行验证。

## 清退手法

按顺序处理，不要直接删干净：

1. **先还原意图。** 这条断言当初想守住什么？写不出来的直接删。
2. **能变成行为断言就改写。** 把被断言的逻辑提取成可调用的函数，用输入输出重写用例。这是最有价值的转化，通常也顺带改善了源码结构。
3. **确实是跨文件架构不变量的，改成扫描式断言。** 例如"全仓库只允许一个请求实例""业务模块不得直接引用某层"。写法要点：按目录扫描当前存在的文件，断言"没有人做 X"，**不枚举**文件清单、模块名、接口路径或数量。枚举本身就是下一次假阳性的来源；扫描式写法在新增模块时自动生效，在正常演进时保持安静。
4. **以上都不成立就删除**，并在交付中说明它原本想守什么、现在由哪一层门禁接管（类型、Lint、评审或真实运行验证）。

## 删除边界

- 一个文件里常常混着真实行为用例与源码文本断言。只清退后者，把前者原样保留，不要因为文件名相近就整文件删除。
- 删除前确认这条行为是否还有别的覆盖点；是唯一覆盖点且行为确实重要时，先补上行为用例再删。
- 清退是一次独立改动，不顺带修改被测源码。源码是否需要改由行为用例的结论决定，不由删测试的顺手决定。
