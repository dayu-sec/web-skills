# 无效测试形态

这里的形态都能跑通、都是绿的、都会被计入用例数量，但它们不执行被测逻辑，因此既拦不住缺陷，又在正常重构时制造红灯。识别它们比多写几条用例更重要。

## 形态一：源码文本断言

把源文件当字符串读进来，用正则匹配其中的片段：样式属性、JSX 属性、`import` 语句、函数签名、接口路径字面量、某段实现文本。

**为什么诱人。** 它不需要渲染环境、不需要造输入、不需要理解被测逻辑，一条断言就能"覆盖"任意文件，而且几乎总能一次写绿。在缺少可执行入口、或者急于给一次改动补上用例时，这是阻力最小的路径，AI 协作下尤其容易成批产出——模型能读到源码文本，却不一定能运行它。

**失败形态。**

- **零拦截。** 不调用任何被测逻辑，业务缺陷一条都发现不了，却在报告里占据覆盖面。
- **等价重构即红。** 抽函数、换等价写法、改类名、挪文件都会让它失败，于是团队养成"改测试让它绿"的习惯，测试从此不再是判据。
- **可能从诞生起就不成立。** 这类断言常与实现同一次提交写入，却从未匹配过实现文本。因为没人把它当行为看，红灯被长期当作待修项挂着。
- **互相矛盾而不被发现。** 一处断言要求某段文本出现、另一处要求同样的文本不出现，两者都能通过编译与运行，只有同时跑测试才会撞上。断言的是文本而非行为，冲突没有任何其它机制能暴露。
- **把一次实现固化成规范。** 它锁住的是"源码长什么样"，直接与重构对立。

**识别信号。** 断言的入参来自读文件的结果；正则里出现样式属性、JSX 属性、`import`、函数签名或目录名；用例名在描述页面结构与布局；用"不得出现某段文本"来表达架构约束；一个用例里连续十几条针对同一文件的正则。

## 形态二：变更探测器

断言一个常量等于它自己的字面量拷贝，或断言配置对象与用例里抄写的副本一致。改一次要改两处，永远不会发现缺陷，只会增加改动成本。区别在于：断言**转换结果**有价值，断言**声明本身**没有。

## 形态三：结构存在性用例

断言某些文件存在、某些旧路径不存在、目录按某种方式组织。目录调整是常规演进，这类用例把它变成一次测试维护；而真正的风险（引用断裂）由类型检查与构建更早暴露。

## 形态四：接线断言

断言组件调用了国际化函数、注册了某个 Hook、引入了某个 Provider。它证明的是代码写了这一行，不是功能可用——文案缺键、命名空间写错、Provider 顺序不对时它照样是绿的。

## 形态五：过宽快照

把整棵渲染树或整个响应对象存成快照。任何无关变动都会让它失败，久而久之快照被无条件更新，等于没有断言。快照只用于小范围、语义明确、人工可读的输出。

## 清退手法

按顺序处理，不要直接删干净：

1. **先还原意图。** 这条断言当初想守住什么？写不出来的直接删。
2. **能变成行为断言就改写。** 把被断言的逻辑提取成可调用的函数，用输入输出重写用例。这是最有价值的转化，通常也顺带改善了源码结构。
3. **确实是跨文件架构不变量的，改成扫描式断言。** 例如"全仓库只允许一个请求实例""业务模块不得直接引用某层"。写法要点：按目录扫描当前存在的文件，断言"没有人做 X"，**不枚举**文件清单、模块名、接口路径或数量。枚举本身就是下一次假阳性的来源；扫描式写法在新增模块时自动生效，在正常演进时保持安静。
4. **以上都不成立就删除**，并在交付中说明它原本想守什么、现在由哪一层门禁接管（类型、Lint、评审或真实运行验证）。

## 删除边界

- 一个文件里常常混着真实行为用例与源码文本断言。只清退后者，把前者原样保留，不要因为文件名相近就整文件删除。
- 删除前确认这条行为是否还有别的覆盖点；是唯一覆盖点且行为确实重要时，先补上行为用例再删。
- 清退是一次独立改动，不顺带修改被测源码。源码是否需要改由行为用例的结论决定，不由删测试的顺手决定。
