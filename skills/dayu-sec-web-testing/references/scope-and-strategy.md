# 测试边界与投入策略

重业务应用的测试资源有限，决定投在哪里比多写几条用例重要得多。没有这条边界，用例会沿着"最容易写"的方向堆积——渲染一下断言 DOM、读一段源码匹配正则——数量涨得快，拦不住任何业务缺陷，最后没人敢信也没人敢删。

## 取舍的唯一框架：业务风险 × 维护成本

每条用例先落到这两个维度上：

- **业务风险**：它守的规则出错时，用户会遇到什么？金额算错、权限放行、状态流转错乱、数据写坏属于高风险；少个图标、间距不对、顺序变了属于低风险。
- **维护成本**：产品常规演进时，这条用例要跟着改几次？断言稳定契约的成本低；断言界面结构、文案、清单顺序的成本高，因为那些本来就该经常变。

**高风险 × 低维护成本**的才值得写，这也是绝大多数值得写的用例的样子。低风险的不写；高风险但维护成本也高的，先想办法把规则从界面里提取成可独立调用的函数，把成本降下来再写。

**不追求覆盖率。** 覆盖率衡量的是"执行到了多少行"，与"守住了多少业务风险"无关；把它当目标，会直接把人推向最廉价的那类断言。目标是关键业务路径、关键业务规则和高风险交互不被回归破坏，不是某个百分比。

## 测试类型的取舍

| 类型 | 典型工具 | 测试对象 | 本团队策略 |
| --- | --- | --- | --- |
| Unit | Vitest / 运行器自带 | 函数、纯逻辑 | **适量做**，主力在此 |
| Component | Testing Library | React/Vue 组件 | **不强制**，仅在组件自身承载业务规则且无法提取时 |
| Browser Component | Playwright Component Testing | 浏览器中的组件 | 不做 |
| E2E | Playwright | 完整 Web 应用 | **不推荐**，关键路径用真实运行验证覆盖 |
| Visual | Playwright / Storybook | UI 视觉结果 | 不做 |
| Accessibility | axe / Playwright | 无障碍 | 不做，由组件库与设计规范承担 |

"适量"是字面意思：Unit 也不是越多越好，同样要过业务风险这一关。

不做的那几类不是不重要，而是**投入产出不成比例**：它们维护成本高、随 UI 常规演进频繁变红，而它们本该守住的东西，在重业务系统里由组件库、设计规范和上线前的真实运行验证承担更划算。团队规模或产品形态变化时这张表可以重议，但重议的是这张表，不是绕过它单独加一类。

## 只测自己的责任

**不测第三方库自身的行为。** 组件库的渲染输出与交互、路由库的匹配、请求库的重试、日期库的格式化、校验库的规则——这些是上游的用例。在本仓库重写一遍，拦不住自己的缺陷，却会在升级依赖时集体变红。

自己的责任是**怎么用**它：传给它的参数对不对、拿回来的结果怎么归一化、失败时怎么分类和降级。测这一层，而不是它的内部行为。

同理，不读第三方包的源码来断言其中的常量或实现细节——那是把别人的实现细节写成了自己的契约。真正需要固定的上游行为，用版本约束和集成时的真实运行验证保证。

## 关键路径 + 业务规则

值得投入的只有两类。

**关键业务路径**：用户完成核心业务目标必经的那条链路，断了产品就不可用。测它的方式不是端到端跑一遍界面，而是把链路上每个决策点的逻辑提取出来单独测——参数组装、响应归一化、状态流转、失败分类。

**关键业务规则**：错了会造成数据错误、权限越界或决策误导的规则。权限与可见性判定、金额与配额计算、状态机的合法迁移、风险等级推导、跨字段的一致性校验。

**普通 CRUD 与低风险 UI 不建议写。** 一个没有特殊规则的列表查询、一个字段直传的表单提交、一个开关控制的显隐，它们的失败形态是显而易见且低成本的，写了只是给每次改动增加一份同步负担。CRUD 里真正值得测的是其中的**非常规部分**：分页越界、并发写冲突、软删除后的可见性、批量操作的部分失败。

## 交付时怎么说

给出的不是用例数量，而是：这次覆盖了哪条关键路径或哪条业务规则、它失败时用户会遇到什么、为什么其余部分没有写。说不出"失败时用户遇到什么"的，就不该出现在交付里。
