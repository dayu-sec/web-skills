# 失败判定

用例红了不等于源码错。改错方向的代价是：要么把正确实现改坏，要么把过期断言抄进源码。在找到可执行真源之前，不修改冲突的任何一侧。

## 先分类

- **断言的是行为**（调用模块、比较输出）→ 默认源码错，按行为修源码。
- **断言的是源码文本、结构或声明**→ 默认先怀疑断言，按 [无效测试形态](ineffective-test-patterns.md) 处理。
- **两条用例互相矛盾**（一条要求出现、一条要求不出现同一事实）→ 两条都不能作为判据，必须去找外部真源。

## 不能当判据的东西

- **投票**：几处写着同一件事不代表它成立。相互印证的断言常常出自同一次提交的复制粘贴。
- **新旧**：新提交不一定照着契约写，旧断言也可能只是当时的一句通则。提交时间不含契约信息。
- **注释、用例名与提交信息**：它们表达意图，不构成证据。
- **"它一直是绿的"**：源码文本断言长期为绿，可能只是因为没人动过那个文件。

## 寻找可执行真源

按顺序取第一个可得的：

1. **仓库内可执行证据**：生成的 SDK 与类型、契约文件、Schema、本地 Mock 定义。它们能直接回答形状问题。
2. **运行中的服务**：仓库内没有契约时，用只读探测确认端点是否存在及其形状。
3. **契约持有方**：前两者都不可得时停下来问人，并把当前证据与两种可能的处置一并说明。不要靠推断二选一。

## 运行中服务的只读探测

可用时这是最硬的证据，但它只在方法正确时成立。

- **只用不改变状态的动词探测。** 不要为了验证一个写操作端点是否存在而真的触发它。
- **靠错误形态而不是状态码区分。** "路由存在但方法或参数不符"与"路由不存在"通常给出不同的错误描述或字段，即使外层状态码被网关统一成同一个值。判据是响应体的形态，不是 HTTP 状态码。
- **必须带对照组。** 同时探测一个已知存在的端点和一个明显不存在的端点，用它们校准这套判据在当前环境下长什么样。没有对照组的单次探测结论不可用。
- **先让凭证自证。** 用一条已知可用的请求确认凭证有效再开始。鉴权失败会把所有路径压成同一种响应，此时任何"存在与否"的结论都不成立——这是这套方法最常见的假阳性。
- **注意凭证的时效与来源。** 持久化存储里的凭证可能已经过期，而运行中的页面持有更新的一份；过期响应与"路由不存在"也可能同形。从页面上下文取凭证时以页面实际发出的请求为准。
- **限定结论范围。** 探测只回答"端点是否存在、形状是否匹配"，不回答响应字段是什么；字段仍以契约为准。
- **不留痕迹。** 凭证、令牌、会话数据不写入日志、结论、文档与提交物；探测使用的临时脚本不留在仓库里。

## 判定之后

- 源码错：按行为修源码，并补上一条真正调用它的用例。
- 断言错：按清退手法处理，并在交付中写明证据链（真源、对照组、结论），不要只写"测试过时"。
- 长期为红或从未成立过的用例，本身就是该用例无效的证据，不要当成源码欠债记账。
