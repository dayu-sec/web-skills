# DayuSec 前端测试

## 工作顺序

1. 读取目标仓库的 `AGENTS.md`、测试命令、测试运行器、用例目录和既有断言风格，确认本仓库测试的真实入口与已成立的约定。
2. 新增或评审用例前，读取 [用例准入](references/test-value-admission.md)，先确认被测对象有可独立调用的入口，并写出这条用例失败时用户会遇到什么。
3. 判断既有用例是否有效、应当改写还是删除时，读取 [无效测试形态](references/ineffective-test-patterns.md)。
4. 用例失败、用例之间互相矛盾，或用例与源码冲突时，读取 [失败判定](references/failure-triage.md)；在找到可执行真源之前，不修改冲突的任何一侧。
5. 按被测对象追加能力 Skill：数据结构、字段与错误体使用 `$dayu-sec-data-contract-first`；URL、方法与状态码语义使用 `$dayu-sec-rest-api`；类型建模与类型级约束使用 `$dayu-sec-typescript`；请求实例与服务边界使用 `$dayu-sec-web-request`；本地 Mock 使用 `$dayu-sec-web-mock`。
6. 删除用例前确认它是否是某条行为的唯一覆盖点：混在同一文件里的真实行为用例拆出保留，只清退断言源码文本的部分，不整文件连坐。
7. 运行目标仓库已有的测试、类型、Lint 与格式命令；区分静态检查、测试通过与真实运行验证，不用其中一种替代另外两种。

## 职责边界

- 本 Skill 只约束"测什么、怎么判断一条用例是否有价值、失败时如何定责"。测试运行器、断言库、目录位置、覆盖率门槛与命令以目标仓库 `AGENTS.md` 和现有配置为准。
- 不复制 React 组件职责、TypeScript 类型规则、请求实例约束、Mock 契约与 UI 规范；这些由对应 Skill 拥有，本 Skill 只说明它们各自适合用哪种门禁守住。
- 目标仓库已有明确且成立的测试约定时以仓库为准，并在交付中说明差异。

## 引用入口

- [用例准入](references/test-value-admission.md)：值得测与不值得测的对象、每条断言必须回答的问题、测试与其它质量门禁的分工、用例颗粒度与命名。
- [无效测试形态](references/ineffective-test-patterns.md)：源码文本断言、变更探测器、结构存在性用例等形态的诱因、失败形态、识别信号与清退手法，含跨文件架构不变量的正确写法。
- [失败判定](references/failure-triage.md)：用例与源码冲突时的定责顺序、可执行真源的寻找次序、运行中服务的只读探测方法及其假阳性清单。

## 输出要求

- 说明被测对象的可独立调用入口、每条用例断言的行为，以及它失败时对应的用户可见问题。
- 列出判定为无效而清退的用例及其形态、改写后保留的部分，以及原本想守的约束现在由谁接管。
- 涉及失败判定时说明真源、对照组和结论方向（源码错还是断言错），并标注哪些验证方式在当前环境会给出假阳性。
- 报告运行过的命令与结果；无法运行时明确缺失的验证证据，不用静态阅读替代。
- 发现源码文本断言、变更探测器、长期为红或从未成立过的断言时，明确报告或修复。
