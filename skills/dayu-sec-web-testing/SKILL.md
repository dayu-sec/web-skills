# DayuSec 前端测试

## 工作顺序

1. 读取目标仓库的 `AGENTS.md`、测试命令、测试运行器、用例目录和既有断言风格，确认本仓库测试的真实入口与已成立的约定。
2. 动手写或评审任何用例前，读取 [测试边界与投入策略](references/scope-and-strategy.md)，先确定这件事该不该由测试来守、属于哪类测试、值不值得投入。边界不先定下来，后面每一步都会漂。
3. 确认要写之后，读取 [用例准入](references/test-value-admission.md)，逐条回答准入三问，并写出它失败时用户会遇到什么。
4. 判断既有用例是否有效、应当改写还是删除时，读取 [无效测试形态](references/ineffective-test-patterns.md)。
5. 用例失败、用例之间互相矛盾，或用例与源码冲突时，读取 [失败判定](references/failure-triage.md)；在找到可执行真源之前，不修改冲突的任何一侧。
6. 按被测对象追加能力 Skill：数据结构、字段与错误体使用 `$dayu-sec-data-contract-first`；URL、方法与状态码语义使用 `$dayu-sec-rest-api`；类型建模与类型级约束使用 `$dayu-sec-typescript`；请求实例与服务边界使用 `$dayu-sec-web-request`；本地 Mock 使用 `$dayu-sec-web-mock`。
7. 删除用例前确认它是否是某条行为的唯一覆盖点：混在同一文件里的真实行为用例拆出保留，只清退断言源码文本的部分，不整文件连坐。
8. 运行目标仓库已有的测试、类型、Lint 与格式命令；区分静态检查、测试通过与真实运行验证，不用其中一种替代另外两种。

## 职责边界

- 本 Skill 只约束"测什么、怎么判断一条用例是否有价值、失败时如何定责"。测试运行器、断言库、目录位置、覆盖率门槛与命令以目标仓库 `AGENTS.md` 和现有配置为准。
- **重业务应用的用例只守业务，且只守高风险的那部分。** 取舍按业务风险 × 维护成本，不按覆盖率。渲染结果、交互行为、布局与样式由组件库和真实运行验证拥有；第三方库自身的行为由上游拥有；普通 CRUD 与低风险 UI 不写。
- **测试类型有明确取舍**：Unit 适量做且是主力，Component 不强制，E2E 不推荐，Browser Component、Visual 与 Accessibility 不做。要突破这张表，重议的是表本身，不是绕过它单独加一类。
- 不复制 React 组件职责、TypeScript 类型规则、请求实例约束、Mock 契约与 UI 规范；这些由对应 Skill 拥有，本 Skill 只说明它们各自适合用哪种门禁守住。
- 目标仓库已有明确且成立的测试约定时以仓库为准，并在交付中说明差异。

## 引用入口

- [测试边界与投入策略](references/scope-and-strategy.md)：业务风险 × 维护成本的取舍框架、六类测试的团队策略、只测自己责任的边界、关键路径与业务规则的定义、普通 CRUD 与低风险 UI 的处理。
- [用例准入](references/test-value-admission.md)：值得测与不值得测的对象、每条断言必须回答的问题、测试与其它质量门禁的分工、用例颗粒度与命名。
- [无效测试形态](references/ineffective-test-patterns.md)：源码文本断言、变更探测器、结构存在性用例、接线断言、过宽快照、组件渲染与交互断言六种形态的诱因、失败形态、识别信号与清退手法，含跨文件架构不变量的正确写法。
- [失败判定](references/failure-triage.md)：用例与源码冲突时的定责顺序、可执行真源的寻找次序、运行中服务的只读探测方法及其假阳性清单。

## 输出要求

- 先说明本次覆盖了哪条关键业务路径或哪条业务规则，以及为什么其余部分不写；不以用例数量或覆盖率作为交付结论。
- 说明被测对象的可独立调用入口、每条用例断言的行为，以及它失败时对应的用户可见问题。
- 列出判定为无效而清退的用例及其形态、改写后保留的部分，以及原本想守的约束现在由谁接管。
- 涉及失败判定时说明真源、对照组和结论方向（源码错还是断言错），并标注哪些验证方式在当前环境会给出假阳性。
- 报告运行过的命令与结果；无法运行时明确缺失的验证证据，不用静态阅读替代。
- 发现源码文本断言、变更探测器、长期为红或从未成立过的断言时，明确报告或修复。
