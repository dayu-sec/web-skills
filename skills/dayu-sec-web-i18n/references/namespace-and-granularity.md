# 命名空间与粒度

文案按命名空间分文件存放，每种语言一份同名文件。命名空间怎么切，决定了并行开发时谁改哪个文件，以及一次术语调整要动多少处。

## 按领域划分，划分即所有权

划分单位是业务领域——围绕同一业务对象的一组能力。判据是这组文案是否随同一批需求一起变化、是否由同一批开发者维护；两者都成立即归入同一命名空间。

命名空间同时是所有权边界：一个领域的文案由该领域的开发者维护，并行开发时各自只改自己那个文件，合并冲突被隔离在领域内部。领域合并或拆分时文案与声明清单一并搬迁，不留下空文件——空文件会让后来者以为该领域没有文案。

其它切法的代价：

- **按页面切**，同一领域的文案散落到多个文件，调整一个业务术语要改多处；页面重组后文件失去归属，没人敢删。
- **按组件切**，命名空间数量随组件增长，声明清单迅速失控，组件复用时文案跟不过去。
- **整个应用一个文件**，所有人改同一个文件，合并冲突集中爆发，这正是划分要避免的结果。

同一领域在多个应用中出现时保持同名，后续搬迁与对照的成本最低。

## 公共命名空间的准入

公共命名空间承载没有领域归属的文案，是应用内唯一的共享面。默认答案是不进，依次问：

1. **是否已有多个领域真实使用？** 只有一个领域在用就留在该领域。"将来可能有人用"不构成理由——搬进去容易，搬出来要协调所有使用者。
2. **脱离上下文后语义是否仍然唯一？** 通用动词、状态词在不同领域可能需要不同译法，进入公共空间后无法分化，只能靠加后缀补救。存在分化可能的留在领域。
3. **是否属于应用级而非领域级？** 应用名称、页面标题、语言与主题、全局导航、通用错误与空态提示没有领域归属，属于公共。

典型误收形态：某个场景专用的占位符或提示语被塞进通用分组，其它领域读到后语义不成立；而修改它会波及全部领域，于是没人敢改，只能再加一个近义键。

新建领域命名空间不需要协调，向公共命名空间搬迁需要协调。这个非对称让低成本的路径同时是正确的路径，是划分能否长期生效的关键。

## 文案粒度

命名空间内按界面结构分组——标题、表格、表单、操作、消息等，不按组件树。结构可预测，接手的人不必逐个文件摸索组织方式；深度保持浅，深层嵌套在调用点会变成长串键名，移动一个分组会波及大量调用点。

键的粒度以一句完整、可独立翻译的文案为单位：

- **不在运行时拼接片段。** 语序随语言变化，拼出来的句子无法通过修改译文纠正，只能改代码。需要变量时用插值占位符，由文案自身决定变量位置；数量、性别等语法差异交给插值与复数规则。
- **同一句文案不在多个命名空间各存一份。** 出现重复是公共命名空间准入的信号，不是复制的理由。
- **键名描述用途而非译文内容。** 译文会改，用途不会；以译文命名的键在文案调整后立刻变成误导。

消费时，只用到本领域文案就声明该领域一个命名空间，需要公共文案时以数组声明、领域在前。命名空间声明一次即可，在每个调用点逐键重复指定会把它的名字散布到整个组件，改名时修改点遍地都是。壳层、菜单等应用级文案由应用统一消费，业务组件不直接读取。
