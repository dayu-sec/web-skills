# 取值时机与句子形态

键组织得再好，取值发生在语言就绪之前，或者句子是运行时拼出来的，界面照样不跟随语言。这两类问题都不会让构建失败，也不会让类型检查报错，只在切到另一种语言之后才显形。

## 取值必须发生在渲染时，不在模块加载时

**模块顶层的表在 `import` 那一刻就求值。** 把枚举码映射成展示名的字典、分区或页签的清单、快捷筛选的预设——这类表按习惯写在模块顶层，而那时语言运行时还没装配完；即便装配完了，之后切换语言也只重建 React 树，这些字符串仍停在旧语言。

处理方式是**表里存键，不存文案**，在渲染时才解析：

- 映射表的值从中文改成键名，字段名随之从 `label` 改为 `labelKey`，让读代码的人一眼看出它需要再解析一次。
- 消费点把 `table[code]` 换成 `t(table[code])`，并保留"表里没有这个码就原样显示"的回退。
- 键名本身不翻译：表的键是服务端下发的码，属于数据。

**函数参数的默认值同样早于 Hook 求值。** 写在 `function <ComponentName>({ children = '<默认文案>' })` 上的默认文案，在 `useTranslation()` 之前就定了。把默认值移进函数体，用 `children ?? t('...')` 表达。

**非 React 模块通过领域出口取值。** 服务层、契约解析、纯函数用不了 Hook，为每个命名空间提供一个 `t(key, options)` 出口，在调用时解析，而不是在模块顶层缓存结果。

## 语言运行时未就绪时的返回值

i18next 在 `init()` 完成前取值返回的是 `undefined`——不是键名，也不是空串。直接用它拼错误消息会得到 `new Error(undefined)`，打印出来只剩一个 `Error`，现场信息全丢。

因此领域出口要统一兜底：**取不到就回退成键名**。界面上露出 `<命名空间>.errors.<键名>` 难看，但能直接定位到缺失的键；露出 `undefined` 或一片空白则既难看又查不下去。

这条兜底也影响测试环境：Node 下跑的用例通常不初始化语言运行时，取值会回退成键名。如果某条既有用例断言的是中文原文，接入 i18n 后它会失败——**改成断言键名，不要为了让它变绿而把文案从源码里留下来**。继续断言中文，等于把"这句没接 i18n"写成了通过条件。

## 句子形态

"键以一句完整、可独立翻译的文案为单位、不在运行时拼接"是粒度规则，归 [命名空间与粒度](namespace-and-granularity.md) 管。这里只说它在落地时的两个形态。

**句子里嵌着标记时用 `<Trans>`。** "共 *12* 条"这种数字带独立样式的写法，直觉是拆成三段 JSX，但那等于把中文语序焊死——英文里数字在前。用 `<Trans>` 把标记位置交给译文表达，组件只提供标签映射；拆成三段就退回了运行时拼接，只是拼接点从字符串挪到了 JSX。

**两句话不共用一个键。** 两处文案只差一个前缀或量词时，复用同一个键会让其中一处永远少掉那部分。键已存在，写在调用点的中文默认值不会生效，所以这个缺陷不会报错，只是安静地显示在界面上。拆成两个键。

## 语言切换的副作用

服务端下发的数据随请求头变化，已经取回的那一份仍是旧语言。应用因此在切换语言后整页重载——这意味着**任何"切换语言后要保留的状态"都必须已经落在 URL 或持久化存储里**，留在内存里的会丢。

同一原因下，日期、数字、货币的格式化要显式跟随应用语言，不能依赖 `toLocaleString()` 的默认行为——它跟的是浏览器语言，与应用内的语言偏好是两回事，切换之后会出现文案已变、日期没变的割裂。
