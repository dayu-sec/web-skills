# 存量中文的识别与分界

把一个领域接入多语言，难的不是搬运，是判断哪些中文该搬。源码里的中文至少有四种身份：界面文案、服务端下发的数据取值、开发者读的日志与错误、以及早已失效的兜底默认值。只有第一种需要接入，其余三种各有各的处理方式，搬错的代价在切到其它语言之后才显形，而且不报错。

## 先找全，再判断

**用能理解语法的扫描，不用正则。** 正则分不清注释里的中文、`t(key, '中文')` 里已经接入的默认值、以及 JSX 文本节点，产出的清单需要人再过一遍，量一大就会漏。按语法树遍历字符串字面量、模板字面量的静态片段和 JSX 文本，把注释排除在外——注释不需要翻译，计入清单只会让数字永远降不到零。

目标仓库已有未提取文案的扫描器或棘轮时以它为准，不要另起一套：两套口径会在数字上互相打架。下调棘轮基线时只动本次真正处理过的文件，并核对其余文件没有跟着变——不加限制地重写基线会把别人的欠账一并抹平，之后再也看不出来。

扫描的结论是一份带上下文的清单：每处中文的所在行、它在语法里的位置（JSX 文本、属性值、对象属性、函数入参），以及它是否已经在某个 `t()` 调用里。位置决定了接入方式，也决定了它是不是文案。

## 文案与数据的分界

**判据是：把它翻译成英文之后，还有没有别的代码依赖这串中文。** 依赖存在就说明它是数据。常见形态：

- **服务端下发的取值**，包括历史遗留的中文枚举。归一化函数里拿中文和后端返回值比对，翻译后分支静默落空，染色、筛选、排序跟着失效，而且不抛错。
- **解析用的分隔符与前缀**。从服务端下发的长文本里切分段落所用的 `<字段名>:` 这类中文标记，翻译后切不出来。
- **对象的键名、权限码、路由片段**。它们参与查表与比对，不面向阅读。

这类中文保留原样，并**就地写注释说明它是数据、为什么不能翻译、翻译后会怎样失效**。注释不是可选项：下一个做 i18n 的人（或模型）第一反应仍然是把它翻译掉，而扫描清单只会告诉他"这里有中文"。

判不准时看调用方向：值从服务端来、代码拿它做比对，是数据；值从代码来、最终进入 DOM 给人读，是文案。

## 错误与日志文本按调用链定去留

抛出的 `Error`、`logger.warn` 里的中文，有的会一路冒泡到 toast 或错误边界，有的从头到尾只进控制台。**逐个追调用链，不按文件或目录一刀切。**

会到用户眼前的信号：上层用 `error.message` 组装提示、把它塞进渲染状态、或交给一个会显示 message 的降级组件。只被 `isError` 布尔消费、被 `catch` 静默吞掉、或只进 logger 的，不接入。

不接入的同样要写注释，写清楚"它停在哪一层"。判断结论不写下来，下次还得重追一遍。

两个容易判错的方向：

- **降级组件的 `message` 覆盖**。调用方自带一句中文 message，把组件里已经翻译好的同类文案顶掉。这种情况的正确处理是删掉这个覆盖，而不是给覆盖再加一个键——同一个故障不该维护两份措辞。
- **启动阶段的失败提示**。如果这段 catch 覆盖的是语言运行时自身初始化失败，那时翻译层还不存在，取值只会回吐键名。这里要先判就绪状态，未就绪才退回中文原文，并写明这是刻意的最后兜底。

## 清退失效的中文默认值

`t('key', '中文')` 里的第二参只在键不存在时才生效。键一旦补齐，这句中文就是死代码——**而且会和译文各自演化**：译文改过几轮之后，源码里留的还是最初那句，读源码的人看到的是一份早已不成立的文案。

处理方式是删掉默认值，不是去同步它。删之前逐条比对键的当前译文与默认值，**不一致的单独记下来交付时点名**：那几处正是源码已经在误导读者的证据，也是这次清退产生价值的地方。

几种变体同样要清：配置表里只用作 `t()` 兜底的 `label` 列、参数默认值上写死的空态文案、手写的按语言分支的三元表达式。它们都建立在"键可能不存在"的假设上，键补齐后假设就不成立了。

例外是被调用签名强制的必填兜底参数。保留，并注明键已存在、走不到这里。
