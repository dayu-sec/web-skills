# 项目结构与发现顺序

## 使用边界

先确认目标仓库是否采用团队默认的多仓库工作区约定。默认结构用于开发工具发现和职责划分，不代表所有微前端框架都必须使用相同目录；已有项目结构与本文不同但职责清晰时，建立角色映射，不为统一目录名进行无关迁移。

## 默认工作区结构

```text
<web-workspace>/
├── project/                       # 项目装配配置仓库
├── container/
│   └── <host-repository>/         # 宿主应用独立仓库
└── microapps/
    ├── <microapp-repository>/     # 子应用独立仓库
    └── ...
```

| 本地角色 | 主要内容 | Git 边界 |
| --- | --- | --- |
| 工作区根 | 聚合配置、宿主和按需拉取的子应用 | 默认不视为业务源码仓库，先检查是否存在 `.git` |
| `project/` | 项目元数据、菜单、装配版本和生成清单 | 独立配置仓库 |
| `container/<host-repository>/` | 宿主运行时、壳层、顶层路由和装配入口 | 独立宿主仓库 |
| `microapps/<microapp-repository>/` | 子应用生命周期、业务路由、页面和局部基础设施 | 每个子应用独立仓库 |

采用团队默认命名时，配置仓库使用 `project-settings-<project-name>`，宿主仓库使用 `container-<project-name>`，子应用仓库使用 `<microapp-name>-<project-name>`；标识采用 `kebab-case`，并尽量让仓库名、包名和应用标识一致。已有项目以实际契约为准，不为统一命名进行无关重命名。

本地 `project/` 是稳定角色名，不要求与远程配置仓库名称一致；`container/` 和 `microapps/` 是本地分组目录，也不代表远程仓库必须存在相同分组层级。执行 Git、安装、Lint、测试和构建命令前，先进入实际独立仓库，不在工作区根假设共享锁文件或统一 Git 历史。

## 项目配置仓库

采用团队默认配置契约时，重点识别：

```text
project/
├── package.json
├── schema/
│   └── meta-schema.json           # 源配置 Schema
├── meta.json                      # 手写装配源数据
├── menu.config.json               # 手写导航配置
└── project.config.json            # 由源配置生成的装配清单
```

- 先读取 `package.json` scripts 和 Schema，再判断生成命令及字段契约。
- `meta.json`、`menu.config.json` 和 `project.config.json` 的实际存在与关系以目标仓库为准；不要在其他架构中凭文件名创建它们。
- 生成文件不手工维护；修改源配置后运行仓库声明的生成命令并检查差异。
- 本地子应用 dev server 地址、代理目标和认证值属于未提交的本地配置，不进入发布装配清单。

## 宿主仓库发现

进入宿主仓库后，按职责定位文件，不假设固定文件名：

| 职责 | 优先检查 |
| --- | --- |
| 工程与命令 | `package.json`、锁文件、工具版本文件、构建配置 |
| 应用渲染入口 | `src` 下的 `main`、`bootstrap`、`app` 或根组件入口 |
| 微前端运行时 | 注册、加载、激活规则、容器挂载和运行时事件相关模块 |
| 项目配置消费 | 配置加载器、Schema/类型、菜单与装配清单读取路径 |
| 路由与壳层 | Router、Layout、Header、Aside、Breadcrumb、挂载边界 |
| 平台上下文 | 身份、权限摘要、主题、语言、请求和监控入口 |
| 本地联调 | dev server、proxy、环境变量和本地目标映射 |

宿主不应存在子应用业务页面、业务表单、业务接口实现或只服务单一业务域的状态。发现这类内容时先确认历史原因和迁移边界，不直接继续扩散。

## 子应用仓库发现

进入子应用仓库后，重点定位：

| 职责 | 优先检查 |
| --- | --- |
| 独立运行入口 | 独立开发时创建应用根和 Provider 的入口 |
| 生命周期适配 | `bootstrap`、`mount`、`unmount` 或框架等价导出 |
| 共享装配函数 | 独立模式和集成模式共同使用的 React/应用装配函数 |
| 路由边界 | Router、basename/base、文件路由生成和子路由入口 |
| 业务视图 | 页面、业务组件、请求、局部状态、类型和样式目录 |
| 应用基础设施 | 主题、语言、请求、Query、错误边界和权限消费入口 |
| 构建与资源 | 构建 base、动态导入、静态资源、开发端口和 SPA fallback |

生命周期文件只适配框架与应用入口；业务实现留在业务视图或功能模块。独立入口和生命周期入口应复用同一装配函数，不维护两套路由、Provider 或主题初始化。

## 发现顺序

1. 读取当前目录及上级可适用的 `AGENTS.md`。
2. 使用 `fd` 或 `rg --files` 查看两到三层结构，确认工作区角色和独立仓库边界。
3. 检查当前目录是否为 Git 根；保留各独立仓库的未提交变更，不在聚合根执行批量 Git 操作。
4. 读取目标仓库的 `package.json`、构建配置、TypeScript 配置和 scripts，确认真实技术栈与验证命令。
5. 使用运行时名称、生命周期导出、Router、basename、base 和配置文件名做定向搜索。
6. 从项目配置映射应用标识、路径前缀和制品版本，再回到对应宿主或子应用仓库修改。
7. 只把完成任务必需的相邻仓库加入上下文；不要默认读取全部子应用源码。
8. 在动手前写清目标仓库、目标角色、源配置、生成文件、运行入口和需要联动的其他单元。

## 允许变体与检查

- 单仓 monorepo 可以把配置、宿主和子应用放在同一 Git 根，但仍保持三个逻辑角色和独立构建边界。
- 独立检出某个宿主或子应用时，可以没有完整工作区；缺少装配信息时再读取配置仓库，不猜路径前缀和版本。
- 框架可能使用 HTML Entry、JavaScript Entry、Module Federation remote 或其他入口形式；以实际构建与运行时配置为准。
- 创建或评审结构时检查：职责是否可定位、源配置与生成文件是否分离、独立仓库命令是否明确、生命周期与业务实现是否分离、局部任务是否无需加载全部工作区。
